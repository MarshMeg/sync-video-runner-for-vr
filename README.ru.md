# Sync Video Runner for VR

[![CI](https://github.com/MarshMeg/sync-video-runner-for-vr/actions/workflows/ci.yml/badge.svg)](https://github.com/MarshMeg/sync-video-runner-for-vr/actions/workflows/ci.yml)

English version: [README.md](README.md)

`sync-video-runner-for-vr` — это небольшой Go-сервис с терминальным интерфейсом для синхронного запуска видео на нескольких телефонах/VR-устройствах.

Он делает две вещи:
1. Принимает регистрацию устройств через `GET /update-ip?id=<device_id>`.
2. Отправляет `GET /start` на все зарегистрированные устройства при нажатии `Ctrl+R`.

## Требования

1. Go `1.25+` (см. `go.mod`).
2. Терминал с поддержкой ANSI escape sequences (Linux, macOS, Windows 10+).

## Быстрый старт

1. Запустите координатор:

```bash
go run ./cmd
```

2. Зарегистрируйте каждое устройство (из приложения на устройстве, браузера или через curl):

```bash
curl "http://<SERVER_IP>:50050/update-ip?id=1"
curl "http://<SERVER_IP>:50050/update-ip?id=2"
```

3. В интерфейсе координатора:
   - `Ctrl+R` отправляет `GET /start` на каждое зарегистрированное устройство (`<device_ip>:8080/start`).
   - `Ctrl+E` очищает список устройств.
   - `Ctrl+C` завершает работу.

## HTTP API

### `GET /update-ip?id=<int>`

Регистрирует или обновляет устройство в памяти:
1. `id` обязателен и должен быть целым числом.
2. IP устройства берется из адреса источника запроса.
3. Порт устройства фиксирован: `8080`.

Ответы:
1. `201 Created` при успехе.
2. `400 Bad Request`, если `id` не передан или не является целым числом.
3. `500 Internal Server Error`, если не удалось определить адрес источника.

## Как это устроено

1. **Хранилище в памяти.** Устройства лежат в map под мьютексом (`internal/server/store.go`). На диск ничего не пишется: после перезапуска координатора устройства регистрируются заново. Интерфейс получает копии записей, поэтому общее состояние читается и меняется только под блокировкой.
2. **Параллельный старт.** По `Ctrl+R` берётся снимок списка устройств, и `GET /start` уходит на каждое устройство из отдельной горутины, то есть все запросы выполняются одновременно. У каждого запроса таймаут 3 секунды: недоступное устройство попадает в строку статуса и не задерживает остальные.
3. **Неблокирующий интерфейс.** HTTP-сервер работает рядом с циклом событий Bubble Tea; рассылка выполняется как команда Bubble Tea, поэтому панель продолжает обновляться (каждые 500 мс), пока идут запросы.
4. **Корректное завершение.** При выходе HTTP-сервер останавливается через `http.Server.Shutdown`, давая завершиться текущим регистрациям.

## Тесты

```bash
go test -race ./...
```

Используется только стандартная библиотека (`testing`, `net/http/httptest`):
1. Хранилище: табличные тесты и тест с конкурентными чтением и записью для детектора гонок.
2. Обработчик `/update-ip`: успех, отсутствующий и нечисловой `id`, повторная регистрация, определение IP из `RemoteAddr`.
3. Рассылка `/start`: проверяется на устройствах-заглушках `httptest.Server`, включая устройство с ошибкой, недоступное устройство, таймаут и проверку того, что запросы действительно идут одновременно.

CI запускает `gofmt`, `go vet`, `go test -race` и сборку при push в `main` и в pull request.

## Сборка бинарников

Используйте скрипт:

```bash
./scripts/build-all.sh
```

Артефакты создаются в `dist/`:
1. `vr-sync-run-linux-amd64`
2. `vr-sync-run-windows-amd64.exe`
3. `vr-sync-run-darwin-amd64`

Опциональное сжатие:
1. Установите `upx` и оставьте значение по умолчанию `USE_UPX=1`.
2. Отключите сжатие: `USE_UPX=0 ./scripts/build-all.sh`.

При пуше тега `v*` те же бинарники собираются в GitHub Actions и прикрепляются к GitHub Release.

## Структура проекта

1. `cmd/main.go` - точка входа приложения (запускает HTTP-сервер и TUI).
2. `internal/server/` - in-memory хранилище устройств, HTTP-обработчик и рассылка `/start`.
3. `internal/tui/` - терминальная панель и обработка горячих клавиш.
4. `scripts/build-all.sh` - скрипт мультиплатформенной сборки.
5. `.github/workflows/` - workflow для CI и релизов.
